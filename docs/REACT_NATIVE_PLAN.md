# CoSpace React Native 移动端开发计划

发布排期会结束后，林知夏在电脑上让 CoSpace 从会议文档提取行动项。离开工位后，她用手机核对原文、负责人和截止日期，点一次确认。陈屿开着的 Web 任务表随即出现分给他的任务。林知夏也可以在手机上把自己的任务标为「进行中」。

首版围绕这条流程开发。按一人全职估算，第 5 个开发日可以演示「电脑生成、手机确认、网页看到任务」，第 10 个开发日完成双平台验收和性能记录。从当前机器配齐原生工具，另留 1–2 个工作日机动时间。

## 产品范围

| 页面 | 用户可以做什么 | 完成条件 |
| --- | --- | --- |
| 连接工作区 | 在已登录的 Web 端取得一次性配对码，在手机输入后看到自己的姓名和角色 | 重开 App 可恢复有效会话。过期时能重新配对，切换账号后只显示该账号的数据 |
| 待确认 | 查看自己在 Web 端生成、尚待处理的行动项建议，按生成时间倒序，下拉可刷新 | 即使其后生成过多条纪要或改写建议，待处理的行动项仍可找到 |
| 建议详情 | 展开生成时保存的文档原文，核对本批任务的标题、负责人和截止日期，选择「确认创建 N 项任务」或「放弃」 | 确认前任务数不变。确认后显示服务端返回的任务，可点进详情。放弃后这条建议移出待办 |
| 任务与详情 | 切换「我的」和「全部」，分页查看任务，在详情将状态改为待办、进行中或已完成 | Web 表格能看到同一条任务的变化。若别人已修改，手机能显示最新状态并让用户重新决定 |

首版沿用 CoSpace 的权限与业务规则。建议由创建者本人跨设备处理，任务在团队工作区内共享。行动项以整批为单位确认，原文展示生成时的快照。协作文档编辑、排期和预算继续使用已有的 Web 页面。推送提醒可在验证用户确实需要离开 App 收到提醒后再接入。

## 现有接口与需要补齐的能力

现状以 2026 年 11 月 18 日的仓库版本 `c9d8c89` 为准。

| 现状 | 对移动端的影响 |
| --- | --- |
| `GET /api/runs` 取当前用户最近 20 次运行，包含纪要、改写和排期。服务端另存了生成时的 `sources` 和结构化 `proposal` | 增加待审列表查询，在数据库先按用户、类型和状态筛选，再分页。详情按运行 ID 读取原文与建议。[生成逻辑](../server/ai.ts) |
| `POST /api/runs/:id/apply` 在同一事务里锁定建议、创建任务、记录 `taskIds`。重复确认会返回同一份结果。`PATCH /api/tasks/:id` 遇到旧版本返回 409 和当前任务 | 两端共用确认事务和版本校验。手机只需正确处理成功、冲突和结果未知三种情况。[API 实现](../server/index.ts) |
| Web 的 `GET /api/workspace` 一次读取所有任务，还包含聊天和文档元数据。网页通过业务 WebSocket 收到任务变更后重新查询 | 手机任务首页使用分页 API。手机提交成功后，已打开的 Web 任务表消费现有事件自动刷新。[Web 工作区](../src/components/workspace.tsx) |
| Web 使用 HttpOnly Cookie，写请求校验 Origin。API 监听本机回环地址。仓库已有 Web/API 回归、万行数据测试和独立的真实模型冒烟流程 | 给原生客户端单独建立会话，以模拟器或 USB 连接本地服务。浏览器回归与原生 E2E 分别留存结果。[架构](ARCHITECTURE.md) · [现有验证记录](VALIDATION.md) |

## 客户端与接口设计

在仓库增加 `apps/mobile/`，采用 Expo development build、React Native、TypeScript、Expo Router 和 TanStack Query。网页继续使用根目录的 Next.js。从 `src/lib/types.ts` 提取两端用到的业务类型，在 `packages/contracts/` 补齐行动项回执与错误契约。共享包只依赖平台无关的代码，两端各自实现请求和界面。第 1 天用开发构建验证 Expo、React、Metro 的版本组合，并给 Web 与 RN 各自划定 TypeScript 检查范围，避免 Next 的根配置把手机代码编入 Web 构建。

手机底部设「待确认」和「任务」两个入口。列表使用 `FlatList` 和稳定的业务 ID，详情使用原生导航。把任务行、状态选择器、来源展开区和提交反馈做成可独立测试的组件。覆盖系统返回、较大字号、读屏按钮名称和提交期间禁用重复点击。建议详情把负责人、截止日与任务标题放在一起，没有截止日时显示「未指定」。

| 能力 | 拟用接口 | 约定 |
| --- | --- | --- |
| 配对与会话 | 新增 `POST /api/mobile/pairings`、`POST /api/mobile/session`、`GET /api/mobile/me`、`DELETE /api/mobile/session` | 网页用已有 Cookie 和正确 Origin 签发短期单次码。手机用码交换独立的不透明令牌，身份和角色由服务端决定。`me` 返回本人和列表所需的成员信息 |
| 待审列表与详情 | 新增 `GET /api/mobile/reviews`、`GET /api/runs/:id` | 列表只取本人 `mode=tasks` 且 `status=ready` 的摘要。两端共用详情接口，按本人权限返回 `sources`、`proposal`、状态和已有回执。移动会话仅可查行动项 |
| 确认与放弃 | 复用 `POST /api/runs/:id/apply` 和 `POST /api/runs/:id/reject` | 原生会话仅可处理本人行动项。服务端校验编辑权限，结果以运行 ID 为准。一个端先处理后，另一个端读回最终状态 |
| 任务列表与详情 | 新增 `GET /api/tasks`、`GET /api/tasks/:id`，复用 `PATCH /api/tasks/:id` | 支持「我的／全部」，默认每页 30 条。以 `created_at` 加 `id` 作稳定游标。移动端改状态只提交 `status` 与读取时的 `version` |

配对码拟定 5 分钟有效，限制尝试次数，在数据库中原子消费。移动令牌沿用现有会话的 24 小时有效期，服务端保存摘要，客户端使用系统安全存储（Expo SecureStore）。浏览器签发、移动端兑换、携带令牌的业务请求分别验证凭据。配对码和令牌均不进入 URL 或日志。过期、撤销或切换身份时清理该账号的本地查询与待核对记录。

手机进入页面、切回前台或恢复联网后立即刷新。待确认页在前台可见时每 15 秒检查一次新建议，进入后台停止轮询。手机确认后，网页任务表根据现有的任务事件刷新。网页的 AI 预览现在将状态放在组件里，计划在重新获得焦点或提交遇到 409 时查询该条建议的详情，让电脑也能显示手机上已做的决定。[Web AI 预览](../src/components/ai-panel.tsx)

网络中断时，进程内保留最近读到的列表和详情，标明更新时间，允许继续阅读。发送确认前，先在本机按账号保存待核对的运行 ID。若响应丢失，显示「正在核对结果」，重连或重启后先查详情。已应用就显示原来的任务 ID，仍是待确认时再让用户决定是否重试。任务状态更新遇到超时同样先读回任务，遇到 409 则展示当前状态和原本想改的值。离线冷启动提示联网，写操作需在线明确提交。

## 十个开发日的排期

| 时间 | 开发工作 | 当天可以验收的结果 |
| --- | --- | --- |
| 第 1 天 | 写出主流程与失败场景的验收示例。搭 RN 工程，先在一个原生目标上跑通，再接入第二个平台。检查共享类型解析、Web 构建和本机连通性 | 在模拟器或 USB 设备打开 App，读取 Fastify 的 `/api/health`。记录实际采用的 Expo SDK、RN、React 和设备版本 |
| 第 2–3 天 | 实现 Web 配对入口、移动会话、按本人筛选的建议列表和详情。补齐过期、重复兑换、只读与跨账号的接口用例 | 林知夏在 Web 生成的建议能在她的手机上读到。陈屿用自己的会话取得同一个 ID 时，看不到该建议 |
| 第 4–5 天 | 完成建议详情、原文展开、整批确认、放弃和应用回执。接上网页任务表，处理双端同时确认与响应丢失 | **首次可演示版本。** 从真实 Web 文档生成一批建议，手机确认，网页自动出现对应任务。再点确认仍是同一批 ID |
| 第 6–7 天 | 完成「我的／全部」分页、任务详情、状态变更、前后台恢复、账号缓存隔离和 409 交互。采集首版任务列表的性能基线 | 两位成员同时操作同一任务时，手机能找回另一端的最新修改。断网期间浏览已打开内容，联网后能核对先前提交的结果 |
| 第 8–9 天 | 用 Maestro 验证原生界面，用 Playwright 驱动网页并校验数据库结果。在 iOS 和 Android 跑主流程，覆盖异常路径，做返回键、大字号和读屏走查 | 两个平台各有一次可重跑的跨端成功记录，关键失败场景有自动化断言。既有 Web/API 用例通过 |
| 第 10 天 | 在同一设备和数据集复测。若基线暴露瓶颈，记录改动前后的样本。整理运行步骤、测试报告及演示录像 | 交付本地 Android APK、iOS 模拟器构建、三分钟跨端录像、带设备与构建信息的性能记录和复现说明 |

本机当前启用的是 Xcode Command Line Tools，`simctl` 不可用，当前 PATH 也没有 `adb`。可先配 Android SDK 和模拟器，或使用 USB Android 设备，通过 `adb reverse tcp:4027 tcp:4027` 访问 Mac 上的 API。iOS 模拟器需要完整 Xcode 和一个 iOS runtime，可直接访问宿主回环地址。原生调试的本地 HTTP 配置限定于演示构建。工具下载期间可以先写接口契约、配对测试和验收样例。

## 自动化验收与 AI 辅助研发

第一条开发规格可以直接写成验收测试。**给定同一位用户已在网页生成含两项任务的建议，当手机确认后丢失响应并重开 App，手机应找回原来的两个任务 ID，网页和数据库里这份建议都只对应两条任务。** 按规格驱动开发（SDD）的方式先写出失败测试，再用 AI Coding 工具协助生成契约、组件草稿和测试数据。人工评审事务、权限和网络恢复逻辑。每一阶段保留规格、测试、代码差异和运行结果。

| 验收场景 | 操作与断言 |
| --- | --- |
| 跨端成功与放弃 | 使用唯一标记生成或准备一批建议。手机确认前，网页任务数不变。确认后，网页显示该批标题，数据库中 `source=runId` 的任务 ID 与回执完全一致。另一条建议放弃后创建数为零 |
| 并发与结果未知 | Web 与手机同时确认同一运行，只产生一批任务。另测服务端已提交、客户端收不到响应，再重开 App 核对。若一端先放弃，另一端展示最终状态 |
| 并发改任务 | 手机打开版本 1，另一成员在 Web 修改任务。手机提交旧版本得到 409，界面显示最新版，由用户决定是否在新版本上重试 |
| 角色与会话 | 编辑者能处理本人建议，另一编辑者按 ID 也无法读取。观察者可看团队任务，写入被服务端拒绝。配对码重复兑换失败，会话失效后返回配对页 |
| 生命周期与分页 | 已读详情断网仍可看，切后台停止轮询，恢复后看见另一端的更新。切换账号清空上个账号的数据。跨页滚动和刷新时按任务 ID 核对遗漏与重复 |

日常 E2E 用带唯一标记的固定建议，在测试数据库准备 `ready` 记录，经过真实 API 和事务。每次演示版本另跑一次真实 Ollama 提取，验证 Web 生成、手机确认和网页回显，并分别记录模型耗时与客户端耗时。自动化运行后只清理该轮标记的数据。

## 原生性能与最终交付

| 项目 | 测量方法 | 首版验收目标 |
| --- | --- | --- |
| 首屏可用时间 | 本地数据库准备 10,000 条任务。固定已登录设备、release 构建和热服务，每次清空该列表的内存查询缓存，从点击「任务」到首行可交互测 30 次，记录 P50/P95 | 首次请求取 30 条，P95 目标 ≤ 1 秒。保留机型、系统、网络方式与原始样本 |
| 滚动稳定性 | 同一台锁定 60 Hz 的 Android 设备连续滚动 15 秒，重复 5 轮，用 Perfetto FrameTimeline 统计错过显示截止时间的帧。iOS 可另用 Instruments 留样 | Android 错过帧占比目标 < 5%。如未达到，先定位数据请求、组件重渲染或原生绘制耗时，再在相同条件复测 |
| 业务一致性 | 同一批建议反复确认、丢弃响应、切后台再恢复，按运行 ID 核对任务数与最终状态 | 同一建议只产生一批任务，旧版本写入无法静默覆盖新值，前后台切换后能恢复服务端状态 |

原生性能目标均待实测。优先在真机记录性能。若交付时只有模拟器，报告标明环境，真机数据单独补测。仓库已有的 Web 万行任务数据可作为同一数据规模的参照，原生帧率和首屏数字由新构建单独采集。

三分钟演示依次展示电脑提取行动项、手机回看原文并确认，以及另一位成员在网页修改任务后手机如何处理冲突。配套材料保留一份规格、同一运行 ID 的跨端 E2E 记录，以及一份可复测的 RN 性能报告。面试时可以用它们解释如何拆需求、如何证明两端交付正确，以及性能改动究竟改善了什么。
